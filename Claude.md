# Development instructions

This repository is a backend-only marketplace for physical products and a long-term learning reference for a React Native developer. Keep the implementation and explanations understandable to someone learning to build APIs for the first time.

Start with [README.md](README.md), the [code index](docs/CODE_INDEX.md), and the README in each folder you will change. Use the [learning path](docs/LEARNING_PATH.md), [Docker guide](docs/DOCKER.md), and [glossary](docs/GLOSSARY.md) for context.

## Required for every change: update documentation and explain why

**Any change to code, configuration, commands, dependencies, tests, architecture, or documentation must include an update to the relevant README files in the same change. Do not consider the work complete until these updates are made.**

- Update the affected folder READMEs to describe the resulting responsibilities, behavior, files, and connections to other modules.
- Update the root [README.md](README.md) when changing setup, running commands, features, shared development conventions, or project-level navigation.
- Explain **why the change was needed** in the relevant README: the problem addressed, the resulting behavior, and any meaningful design tradeoff. Describe the current design and its rationale so the file remains useful as a reference.
- Update related guides when affected: API contracts and examples, React Native integration, Docker commands, environment configuration, deployment steps, testing instructions, and the learning path. Add unfamiliar backend terms to the glossary with a plain-language explanation and a code reference.
- Keep links and the code index accurate when adding, moving, renaming, or deleting files. Every new maintained folder needs a README; generated folders, caches, secrets and dependencies remain excluded.
- For a documentation-only correction, explain the ambiguity or outdated instruction it fixes in the relevant README.

### Edit generated documentation at its source

Folder READMEs and the code/API/configuration indexes are generated by [scripts/generate_docs.py](scripts/generate_docs.py). Update the relevant `PURPOSES`, `FILE_HELP`, or generation logic first, including the explanation of the design where applicable. Then regenerate; do not rely on manual edits that the next generation will overwrite.

The root README and handwritten learning guides are edited directly. Regeneration does not replace the need to update those guides or check that the explanations match the actual code.

```bash
# After make setup; these commands do not require uv on the global PATH:
.venv/bin/python scripts/generate_docs.py
.venv/bin/python scripts/check_docs.py
```

The documentation checker verifies folder README coverage and local links. It does not verify that prose, business rules or examples are correct; review those yourself.

### Explain the change when handing it back

In the final response and in any PR description, state:

1. What changed and where.
2. Why the change was made and what behavior it improves or fixes.
3. Which READMEs/guides were updated, with links.
4. What was checked and the actual result; identify anything not verified or still incomplete.

Use plain language, explain necessary backend terminology, and never describe a check as passing unless it was run successfully. Keep this explanation proportional to the change.

## Development workflow

- Inspect the existing implementation, local instructions and working-tree changes before editing. Preserve unrelated user work.
- Follow existing domain patterns and keep changes scoped to the requested behavior. Search for callers, related schemas, tests and documentation before changing a shared interface.
- Use the [Makefile](Makefile) for repeatable commands. It detects project-local uv and supplies local Docker user/group IDs.
- Run Docker commands from the repository root with Docker Desktop running. `make setup`, `make up`, and `make seed` prepare the local environment; `make demo` creates an actual local order with a simulated payment.
- Use `make logs` and `make ps` to investigate startup. The migration container exiting with code 0 is expected. `make down` preserves named database volumes; do not remove persistent data as a routine fix.
- Rebuild/recreate the appropriate services after source or environment changes. `make up` handles the core stack; `make all` handles all labs. A plain container restart does not load changed environment values or rebuild source.

## Application architecture

- Keep HTTP parsing, dependency declarations and response contracts in `router.py`; request/response validation in `schemas.py`; business workflows in `service.py`; reusable queries in `repository.py`; and database mappings/constraints in `models.py`.
- Do not add empty layers just to match a directory pattern. Simple reporting queries may be called directly from a router, as in analytics.
- Register new routers in [src/app/api/v1/router.py](src/app/api/v1/router.py) and mapped models in [src/app/db/models.py](src/app/db/models.py).
- This is a modular monolith with one shared marketplace schema. Sellers are isolated by record ownership checks. Legacy tenant provisioning/session examples and `domains/example` are reference material, not active marketplace features.
- Treat `/api/v1` as a client contract. Explain API changes and update schemas, examples, role documentation and React Native integration guidance together. Keep lists bounded and response models explicit; never expose stored password hashes or internal credentials.

## Authentication and authorization

- Public registration permits only buyer and seller roles. Provision staff through the operational CLI; never accept public role escalation.
- Apply both role checks and object ownership checks. A seller role does not grant access to another seller's products or order items.
- Use [api/deps.py](src/app/api/deps.py) so protected requests check the current database session, account status and permissions. Preserve token expiry, issuer/audience validation, refresh rotation and revocation behavior.
- Keep secrets outside source control and images. Do not log passwords, tokens, full addresses or provider credentials. Preserve production configuration guards and local-only demo restrictions.

## Database and transaction rules

- Use `DbSession` for active marketplace APIs. Authentication, ownership, checkout and reads that must observe recent writes use the primary database.
- Replica-backed reporting requires an explicit marketplace-scoped dependency and a documented consistency policy. Do not route authorization/session/checkout reads to a replica.
- Business mutations must commit their audit and outbox records in the same transaction. Use [events/service.py](src/app/domains/events/service.py), not the retained best-effort template audit client.
- Preserve row-lock ordering, database constraints and idempotency protections in inventory, checkout, payment, cancellation, expiry, refunds and settlement flows. A check followed by an unlocked update is not sufficient for concurrent requests.
- Add a new Alembic revision for schema changes. Review generated DDL and data migration behavior; never rewrite a revision already deployed. Test migration changes against a disposable database. A downgrade can delete data and is not a backup strategy.
- Dispose both primary and optional replica pools through `dispose_engines()` during shutdown.

## Money, orders and external integrations

- Store monetary values as integer minor units with an explicit currency. Do not use floating point for financial calculations or combine currencies in reports.
- The server determines prices, stock, commission and allowed state transitions. Never trust client-supplied payment success, seller ownership, currency conversion or a cart total without validation.
- Preserve price/address/commission snapshots on historical orders. Keep checkout retries and repeated payment/refund operations idempotent.
- Kafka delivery is at least once. Preserve durable outbox retries and stable event IDs; consumers must deduplicate and tolerate the documented ordering limits.
- Local payments/refunds are simulations; email delivery is a local token flow; settlement records do not transfer funds. Do not describe these as live-provider integrations. Update [deployment readiness](docs/DEPLOYMENT.md) and [payment boundaries](docs/MONEY_AND_PAYMENTS.md) when those capabilities change.

## Verification before completion

```bash
make check   # Lint, formatting, strict source typing, documentation checks
make test    # Full tests; integration tests require PostgreSQL/Docker
make config  # Validate base and lab Compose configurations
```

Run checks appropriate to the change. For application changes, run `make check` and the relevant tests, then the full suite where shared behavior or the coverage gate is affected. Keep the existing 85% coverage requirement; do not lower it or weaken tests to hide failures. Add meaningful regression tests for changed business rules, permissions, concurrency or failure handling.

For Docker/setup changes, validate Compose and smoke-test affected running commands in an isolated project when feasible. For documentation-only changes, check links and review instructions; do not claim a new runtime test result based on an older run. Do not create implementation-mirroring tests for simple reversible documentation or formatting edits.

Update [the verification record](docs/VERIFICATION.md) only with checks actually performed. Complete the README updates and the explanation of why the change was made before handing the work back.
